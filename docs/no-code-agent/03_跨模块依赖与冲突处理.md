# 跨模块依赖与冲突处理

`/full` 的唯一业务顺序是：`M1 → M2 → M6 → M3 → M4 → M5`。每个模块读取前序的 `module_state` 与 `benchmark_registry`，并将自己的输出写回同一 `run_id`。该顺序是零代码流程纪律，不表示当前代码运行时已经自动实现同样的编排。

## 1. 前序要求与缺口处理

| 模块 | 前序要求 | 可用的安全默认值 | 不可推断的缺口 |
| --- | --- | --- | --- |
| M1 | 品牌范围、目标期、可用证据 | 仅建立公开观察样本清单 | 竞品真实预算、定向、订单和账户表现 |
| M2 | M1 的赛道/观察边界 | 以用户声明的人群或 `E_策略假设` 生成测试角度 | 真实受众画像、偏好和转化归因 |
| M6 | M1、M2 的主题边界 | 建议关键词分层和验证清单 | 平台真实搜索量、热度排名和竞价 |
| M3 | M2 人群、M6 关键词、达人输入 | 仅生成筛选标准与待核验名单 | 虚构达人、真实报价、档期和履约能力 |
| M4 | M3 候选、指标登记和审批边界 | 小范围测试建议或“待计算” | 真实聚光定向、竞价、转化和可执行投放 |
| M5 | M4 测试方案及所有选定指标 | 只生成区间化节奏草案 | 正式预算、采购、下单与放量指令 |

安全默认值只允许建立待验证方案，不能把不可推断的缺口写成事实。任一模块缺少硬性前序时，标记 `blocked` 或 `completed_with_gaps`，列入 `unresolved_gaps` 与人工复核，而不是继续推断。

## 2. 冲突优先级

发生冲突时，保留全部候选值、来源和期间，并按以下冲突优先级选择或升级：

1. 同期且适用的 `A_官方或授权`；
2. 同期且范围清晰的 `C_用户导入`；
3. 可复查且样本范围明确的 `B_公开观察`；
4. 有来源、适用条件匹配的 `D_行业基准`；
5. `E_策略假设`；
6. `Mock`（只能用于模拟，不能参与正式选择）。

若优先级相同但数值或口径不同，停止下游正式计算，写明差异、需要的证据和人工裁决。任何证据不得越过其允许结论范围。

## 3. 预算守恒失败

`M5` 必须验证：各渠道/阶段预算之和等于批准的总预算，且 `recommended_ratio` 的分配不混入 `scenario_ratio`。发生预算守恒失败时，禁止输出正式预算、采购或下单结论；返回冲突项、差额、计算口径和修正建议，并创建 `human_review_items`。

## 4. 全案结束检查

全案结束检查至少包括：

1. 顺序是否为 `M1 → M2 → M6 → M3 → M4 → M5`，且每个前序状态可追溯；
2. 每项事实、数字和建议是否有证据 ID、期间、来源、公式或假设标签；
3. 是否仍有不可推断缺口、冲突或低置信度项未升级人工复核；
4. `Mock` 是否完全隔离，未进入采购、下单或正式预算；
5. 所有模块是否引用同一版 `benchmark_registry`；
6. 预算是否守恒，推荐比例与情景比例是否分开；
7. 是否已列出预算放量、达人合作、合规和真实性的人工审批项。
