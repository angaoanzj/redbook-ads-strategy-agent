# 代码版与零代码版小红书策略 Agent 架构设计

## 1. 目标

以现有 `xiaohongshu-strategy-agent` 的实际代码为事实来源，完成两阶段交付：

1. 更新代码项目的技术架构文档和架构图；
2. 从现有六模块实现中提炼可用于 Claude Project 与自定义 GPT 的零代码主控 Prompt、六份模块 SOP 及配套治理文件。

两种运行形态共享相同的业务模块、证据纪律、指标口径和输出边界。零代码版不得描述代码版尚未实现的能力，技术架构文档也不得把规划状态写成当前能力。

## 2. 设计原则

- **代码事实优先**：架构描述和 SOP 字段必须能追溯到当前代码、数据表或明确标注的规划项。
- **业务同源、运行形态分离**：代码版负责稳定计算、持久状态和程序化审计；零代码版负责低门槛部署和交互式分析。
- **证据等级不可降级伪装**：官方/授权、公开观察、用户导入、行业基准、策略假设和 Mock 必须分别标识。
- **单一事实源**：CPC、CPM、CPA、CTR、CVR、ROAS、搜推比例和预算基准只能从统一指标注册表选用。
- **确定性回退**：模块 Agent 不可用或输出不合法时，代码版回退确定性模块；零代码版回退 SOP 的证据不足路径。
- **人工最终审批**：预算放量、达人采购、素材发布和账户操作始终保留人工拍板。

## 4. 代码版目标架构描述

### 4.1 核心组件

| 组件 | 当前代码依据 | 职责 |
| --- | --- | --- |
| Web/API | `main.py`、`web/` | 接收输入、返回报告、维护会话标识与幂等键 |
| 数据契约 | `models.py` | 校验品牌、预算、证据和模块输出输入 |
| 证据知识库 | `knowledge_base.py`、`xhs_knowledge.db` | 保存、去重、检索公开笔记、规则和品牌历史数据 |
| 状态库 | `agent_state.py`、`agent_state.db` | 保存会话、分析记录、checkpoint、反馈、缓存和幂等状态 |
| 证据审计 | `engine.py` | 识别证据缺口，限制无依据结论 |
| 确定性引擎 | `engine.py` | 生成六模块基线策略、预算守恒和降级报告 |
| 模块 Agent | `module_agents/module1.py` 至 `module6.py` | 基于受控证据执行模块级决策 |
| 工具层 | `tools/` | 提供预算、竞品、选题、达人、关键词、出价和预测等可验证计算，并由工具注册表暴露给模块 Agent |
| 模型双通道配置 | `model_config.py` | 分离 Analyzer 与 Embedding 配置，兼容旧 `AGENT_OPENAI_*` 环境变量；Analyzer 已用于模块 Agent/报告，Embedding 当前为已配置、待接入向量检索 |
| 决策视图 | `report_agent_view.py` | 将 `agent_decision` 和 Grounding Check 转为报告视图 |
| 报告渲染 | `report_view.py` | 生成管理摘要、章节、执行方案和 Markdown |
| 数据模拟服务 | `mock_agents.py`、`mock_scenarios.py` | 仅在显式允许时按缺口生成可复现模拟证据，不覆盖真实数据，不作为正式决策来源 |
| 容器部署 | `Dockerfile`、`docker-compose.yml` | 构建 API 服务、映射 8010 端口、挂载数据卷、透传双通道模型配置并执行健康检查 |

### 4.2 业务依赖

全案的业务依赖顺序为：

```text
M1 赛道与竞品
  → M2 用户画像与选题
  → M6 关键词发现与分层
  → M3 达人匹配
  → M4 聚光投流决策
  → M5 全域预算与节奏
```

文档必须区分该目标依赖和当前代码执行顺序。如果当前模块仍由共享请求并行生成，应标注为“当前实现”，把串行状态传递列为演进项。

### 4.3 决策优先级

```text
合规证据输入
  → 确定性模块基线
  → 模块 Agent 决策
  → 输出契约校验
  → Grounding Check
  → Agent 决策进入报告

Agent 失败 / 契约失败 / 数字未通过溯源
  → 回退确定性模块
  → 标记 decision_source 与人工复核项
```

### 4.4 模型通道现状

- **Analyzer 通道**：供模块 Agent 决策和可选报告润色使用，已经进入运行链路。
- **Embedding 通道**：`model_config.py` 和 Docker Compose 已提供独立 Key、Base URL 与模型配置，但当前知识库仍以 SQLite FTS5/混合排序为主，尚未调用 Embedding API。

技术架构图必须把 Embedding 标成“配置就绪、向量检索待接入”，不能画成已运行的数据流。

### 4.5 模型职责演进

历史版本中模型仅用于报告表达润色。当前版本已经增加六模块 Agent，模型可以在工具和输出契约约束下生成模块决策；报告润色仍是可选路径。确定性引擎继续承担预算守恒、基础策略、证据不足降级和 Agent 失败回退，因此架构文档不得继续使用“模型只润色”概括当前系统。

## 5. 零代码版架构

### 5.1 三层结构

1. **System Instructions / Orchestrator**：负责角色、命令路由、执行顺序、全局纪律和最终汇总。
2. **Knowledge Files / SOP 与数据规范**：承载六模块执行逻辑、证据等级、冲突处理、指标注册表和输出模板。
3. **Conversation State / module_state**：每个模块结束时生成机器可读状态摘要，供后续模块引用。

零代码版不把自由对话全文视为可靠状态。后续模块只能引用前序 `module_state.confirmed_facts`、`decisions`、`benchmark_registry` 和 `unresolved_gaps`。

### 5.2 路由

- `/m1` 至 `/m6`：运行单模块；
- `/full`：按 `m1 → m2 → m6 → m3 → m4 → m5` 运行；
- `/ab`：在已完成模块结果基础上生成 A/B 测试矩阵；
- `/board`：把已有结构化结果转换为看板数据，不补造新事实。

### 5.3 模块 SOP 统一结构

每份 SOP 必须包含：

1. 职责与禁止越界；
2. 必需输入、可选输入和安全默认值；
3. 前序模块依赖；
4. 允许的数据来源和证据等级；
5. 执行步骤、工具替代方法和计算规则；
6. 结构化输出模板；
7. `module_state`；
8. 数字 Grounding 自检；
9. 缺数据降级路径；
10. 需人工拍板事项。

## 6. 数据和证据纪律

| 等级 | 类型 | 可用于何种结论 |
| --- | --- | --- |
| A | 官方规则、品牌授权账户数据 | 正式事实与账户决策基准 |
| B | 可核验公开页面观察 | 样本内结论，不外推平台大盘 |
| C | 用户导入历史文件 | 指定品牌和时间范围内的历史事实 |
| D | 有来源的行业基准 | 测试区间参考，不覆盖账户实测 |
| E | 策略假设 | 只能转成测试方案 |
| Mock | 明确模拟数据 | 仅演示，不进入采购、下单和正式预算结论 |

Web Search 搜不到竞品真实预算、真实定向、成交订单或聚光账户数据时，必须输出“不可确认”和补数方式，不得以行业逻辑补成事实。

真实历史数值保留精确值；预测、建议出价和预算方案使用区间。每个数值必须带来源、期间、计算方式或明确的假设标签。

## 7. 指标单一事实源

所有模块共享 `benchmark_registry`。同一指标多来源时必须保存候选值，并根据“授权账户/品牌历史优先、时间适用性优先、行业基准后置”的规则选出 `selected_value`。下游模块只能引用选定值，并附 `selected_source` 和 `selection_reason`。

搜推比例同时区分：

- `recommended_ratio`：正式建议，进入预算计算；
- `scenario_ratio`：测试情景，不进入正式预算汇总。

## 8. 容错与冲突处理

- 前序模块缺失：列出默认假设并降低置信度；不可默认的数据保持缺口。
- Agent 输出不完整：代码版回退确定性结果；零代码版按 SOP 补齐结构，但不得补造事实。
- 数字冲突：列出全部候选来源，强制选用并解释；未解决前禁止进入预算计算。
- 预算不守恒：停止输出正式预算，返回冲突项和修正建议。
- Mock 混入正式结论：阻止下单型建议，并在报告顶部显示风险标识。
- Web Search 不可用：使用已注明日期的知识文件；知识库也无依据时输出缺口。

## 9. 测试与验收

### 9.1 架构文档验收

- 每个代码组件可对应到当前真实文件；
- 架构图覆盖输入、检索、审计、六模块、Agent、报告、状态与人工审批；
- 明确区分当前实现和目标演进；
- 双版本能力映射包含能力、实现方式、差距和补偿措施。

### 9.2 零代码包验收

- Claude 与 GPT 入口引用同一组共享知识文件；
- 六份 SOP 的职责、输入和输出与代码模块一致；
- `/full` 顺序固定为 `m1 → m2 → m6 → m3 → m4 → m5`；
- CPC、CPM、CPA、CTR、CVR、ROAS、搜推比例和预算使用统一注册表；
- 无证据时不生成竞品账户、真实定向、虚假达人、伪热搜或效果承诺；
- 每个模块输出 `module_state`、证据边界、置信度和人工复核项；
- 曲奇四重奏示例同时展示真实、公开观察、缺口和 Mock 边界；
- 全案结束时执行数字来源、预算守恒、Mock 隔离和跨模块冲突检查。

## 10. 非目标

- 本阶段不新增数据爬取能力；
- 不接入或操作真实聚光账户；
- 不绕过登录、验证码或访问控制；
- 不把 Claude/GPT 的会话上下文包装成持久数据库；
- 不建立两套独立业务 SOP；
- 不承诺零代码版达到代码版的程序化校验强度。
