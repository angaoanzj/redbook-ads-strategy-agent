# 小红书策略 Agent 人可读分析报告设计

## 1. 背景与问题

当前系统已经能输出六模块结构化数据、证据来源、Mock 标识和 Markdown，但网页默认把模块对象递归渲染为字段树。用户看到的是“证据审计界面”，而不是一份能够供面试官、管理层和投手阅读的策略分析报告。

作业要求中的“自然流量大盘、聚光投放大盘、竞品全域投放拆解、风险预警”是报告必须覆盖的取材点，不应直接作为 JSON 字段目录展示。系统需要解释数据、形成判断、给出行动，并保留证据可追溯性。

## 2. 目标

将结果页改造成 A + C 混合形态：

- 以“管理层决策报告”为主要阅读体验；
- 用指标卡、趋势图、预算结构图和表格支撑结论；
- 为投手提供可执行的优先级、预算、指标和止损动作；
- 将结构化证据树降级为默认折叠的附录；
- 真实数据、公开资料、Mock 和数据缺口继续明确区分；
- 不依赖大模型也能稳定生成完整报告，大模型仅负责可选润色。

## 3. 用户与阅读路径

### 3.1 管理层／面试官

需要在 30 秒内获得：

- 一句话战略判断；
- 3–5 个关键发现；
- 核心预算建议；
- 主要机会与风险；
- 下一步优先动作。

### 3.2 投手／运营团队

需要进一步获得：

- 每项判断的数据依据；
- 内容、关键词、达人和聚光的具体动作；
- 预算、负责人、时间、验证指标和止损条件；
- 真实证据与模拟情景的边界。

## 4. 页面信息架构

结果页提供三个一级入口：

1. **分析报告**：默认打开，人可读的完整策略报告。
2. **执行方案**：P1／P2／P3 行动清单和投放操作表。
3. **证据附录**：原六模块结构化数据、来源、证据等级、Mock 种子和缺口明细。

下载 JSON 继续导出完整结构化响应；下载 Markdown 导出与页面分析报告相同的叙事内容。

## 5. 报告主体结构

### 5.1 管理层决策摘要

报告顶部必须包含：

- 报告周期与分析范围；
- 一句话战略判断；
- 核心机会、预算重点、主要风险和数据可信度；
- 3–5 条关键发现；
- 3 条最高优先级行动。

关键发现不能只是复述指标，必须回答“该数据对本次投放意味着什么”。

### 5.2 第一章：自然流量大盘分析

必须覆盖：

- 笔记发布量与互动量趋势；
- 流量高峰时段；
- 热门／候选平台标签；
- 内容热门形式。

呈现方式：

- 趋势指标卡；
- 30 天趋势图或当前证据覆盖期趋势图；
- 高峰时段和内容形式表；
- 2–4 段分析文字；
- 对内容生产和发布时间的行动建议。

若数据来自关键词搜索样本，必须称为“样本内趋势”，不得称为真实全平台大盘；若使用模拟平台大盘，章节标题旁显示 Mock 标识和种子。

### 5.3 第二章：聚光投放大盘分析

必须覆盖：

- CPC、CPM、转化成本；
- 热门推广目标（种草／成交／客资）；
- 搜索与信息流预算占比；
- 2026 年平台流量探索方向。

呈现方式：

- CPC／CPM／CPA 指标卡；
- 搜索与信息流预算环形图；
- 低／中／高情景表；
- 对指标含义、预算理由和测试策略的分析文字；
- 账户数据替换规则与验证周期。

无真实聚光账户证据时，不使用“行业平均”或“2026 最新事实”等确定性表达；必须称为“模拟测试情景”或“待验证探索方向”。

### 5.4 第三章：竞品全域投放分析

必须覆盖：

- 自然流量爆款共性；
- 内容空白和差异化机会；
- 带广告标识的投流笔记识别；
- 内容类型和观察／投放时长；
- 评论区受众信号形成的定向测试假设；
- 大致预算验证情景。

呈现方式：

- 先输出竞争判断和建议，不先展示账号表；
- 再展示竞品对比表；
- 广告标识、时长、定向、预算分别显示证据状态；
- 无法证明的内容明确标注“假设”，不得写成竞品事实。

### 5.5 第四章：风险与合规建议

必须覆盖：

- 近期被限流／违规的内容类型；
- 聚光广告拒审高频原因；
- 官方规则底线；
- 对本品牌素材和投放的影响；
- 发布前检查和拒审后处理动作。

官方规则列表与账户／赛道违规频次台账继续分开。没有频次台账时，不能把规则条文称作“近期高频”。

## 6. 统一分析段落契约

每个报告章节按以下顺序生成：

1. **决策结论**：一句明确判断；
2. **数据说明**：关键指标、时间范围和样本量；
3. **原因分析**：解释趋势、关联或差异；
4. **建议动作**：说明具体做什么；
5. **验证指标**：定义成功、继续或停止标准；
6. **证据边界**：说明真实、公开、Mock 或缺失状态。

当证据不足时仍输出可执行的补数或测试动作，但不能生成无依据事实。

## 7. 执行方案

执行方案按 P1／P2／P3 排序，每项包含：

- 动作名称；
- 为什么做；
- 具体步骤；
- 预算或资源；
- 负责人角色；
- 计划时间；
- 成功指标；
- 止损或升级条件；
- 依赖证据。

P1 为立即执行且高影响动作，P2 为本周期执行，P3 为需要进一步证据或资源的验证动作。

## 8. 图表与视觉层级

首版只实现有明确决策价值的轻量图表：

- 自然流量发布量／互动量双序列趋势图；
- 搜索／信息流预算环形图；
- 关键指标卡；
- 高峰时段、内容形式、竞品和风险表格。

不引入重型图表依赖；优先使用原生 HTML、CSS 和 SVG。图表必须显示单位、时间范围、数据类型和空值状态，不得用零替代缺失值。

## 9. 报告生成架构

### 9.1 后端

在确定性策略引擎中增加独立的报告视图模型组装层。该层只读取现有六模块结果，生成：

- `executive_summary`；
- `report_sections`；
- `action_plan`；
- `evidence_appendix` 引用信息。

同一视图模型同时驱动 Markdown 和网页，避免页面报告与下载报告结论不一致。

### 9.2 大模型

大模型仅允许润色已经生成的报告文字：

- 不新增指标；
- 不改变预算、证据等级或 Mock 标识；
- 不删除证据边界；
- 模型不可用时使用确定性报告，不影响完整性。

### 9.3 前端

前端默认渲染报告视图模型：

- 摘要卡；
- 章节文字；
- 图表和决策表；
- 行动方案；
- 折叠证据附录。

现有通用树形渲染器只用于“证据附录”。

## 10. Mock 与证据规则

- 真实／授权数据始终优先于 Mock；
- Mock 指标卡、图表、表格行和结论旁均显示 Mock 徽标；
- 页面显示当前 `mock_seed`；
- 相同请求和种子生成相同报告与图表；
- Mock 不得被表述为平台最新事实、竞品真实投放或真实达人推荐；
- 证据不足时使用“待验证”“模拟测试情景”“样本内趋势”等准确措辞。

## 11. 异常与降级

- 无趋势数据：显示缺口说明和补数动作，不渲染空图；
- 无真实聚光数据：显示 Mock 情景或账户导入要求；
- 无竞品证据：给出采样计划，不生成真实竞品结论；
- 大模型失败：保留完整确定性报告；
- 某章节异常：其他章节仍可显示，异常章节给出明确错误与恢复动作；
- 页面必须保持中文字段和人可读文案。

## 12. 测试与验收标准

### 12.1 后端测试

- 四个必需章节全部存在；
- 每章均有结论、分析、行动、验证指标和证据边界；
- 报告视图模型与 Markdown 使用相同数据；
- 相同种子报告一致，不同种子 Mock 报告变化；
- 真实证据不会被 Mock 结论覆盖；
- 无数据时不出现虚假数字或错误的确定性措辞。

### 12.2 前端测试

- 默认入口为“分析报告”；
- 页面存在“分析报告／执行方案／证据附录”三个入口；
- 趋势图、预算图、指标卡和关键表格能从响应数据渲染；
- 证据树只在附录出现；
- Mock 徽标和种子可见；
- 下载 Markdown 与页面报告结构一致。

### 12.3 人工验收

- 管理层可在 30 秒内说出核心策略、预算重点和第一优先动作；
- 投手能找到具体动作、指标和止损线；
- 用户无需展开证据树即可理解四章分析结论；
- 用户仍能从附录追溯每个关键结论的数据来源。

## 13. 非目标

本次不实现：

- 实时小红书采集；
- 聚光账户自动登录或私有报表同步；
- PDF／PPT 导出；
- 重型 BI 仪表盘；
- 让大模型自由补造缺失数据；
- 重构与报告无关的知识库或采集器。
